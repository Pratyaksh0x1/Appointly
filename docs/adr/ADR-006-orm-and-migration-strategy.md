# ADR-006: Database Tooling and Migration Strategy (Drizzle ORM on Neon Postgres)

## Status

Accepted

## Context

Phase 2 requires an expanded relational schema on PostgreSQL with strict concurrency guarantees:

- 8 core tables: `doctors`, `appointment_types`, `patients`, `appointments`, `slot_holds`, `calls`, `outbox`, and `callback_requests`.
- Strict unique constraint: `UNIQUE(doctor_id, slot_start) WHERE status = 'CONFIRMED'` to prevent two active appointments on the same slot while allowing cancelled/rescheduled history.
- Atomic transaction requirements: Slot generation, 2-minute auto-expiring slot holds, idempotent bookings, and cancellation/rescheduling.
- Integration with Neon Serverless PostgreSQL and connection poolers.

We evaluated three options:

1. **Prisma ORM**
2. **Plain Unmanaged SQL**
3. **Drizzle ORM**

## Decision Drivers

- **Zero Binary Bloat & Cold Starts**: Voice agents require sub-second latency; engine binaries add cold-start overhead and deployment fragility.
- **Support for Partial Unique Indexes**: Crucial for clinic booking (`WHERE status = 'CONFIRMED'`).
- **Connection Pool Compatibility**: Neon requires `-pooler` connection strings for high-concurrency web requests and direct strings for migrations.
- **Type Safety**: End-to-end TypeScript types inferred directly from schema definitions without manual type sync.

## Options Comparison

| Criterion                     | Prisma ORM                                | Plain SQL                     | Drizzle ORM (Chosen)                          |
| :---------------------------- | :---------------------------------------- | :---------------------------- | :-------------------------------------------- |
| **Runtime Overhead**          | Heavy C++ engine binary (~60MB)           | Zero runtime overhead         | Zero runtime overhead (pure TS)               |
| **Type Safety**               | High (generated client)                   | Manual typing required        | 100% inferrable TypeScript                    |
| **Partial Unique Indexes**    | Not natively supported in DSL             | Full native support           | Full native support (`uniqueIndex().where()`) |
| **Transaction & Row Locking** | Interactive transactions (`$transaction`) | Native `BEGIN` / `FOR UPDATE` | Native `db.transaction()` & `for('update')`   |
| **Neon Best Practices**       | Requires data proxy or adapter            | Supported                     | Official Neon recommended ORM                 |
| **Migration Management**      | Shadow DB required                        | Manual migration scripts      | `drizzle-kit` SQL migrations & push           |

## Decision

We adopt **Drizzle ORM** (`drizzle-orm/node-postgres`) paired with **Drizzle Kit** for schema migrations on Neon PostgreSQL:

1. **Schema Definition**: Schemas are declared in TypeScript (`src/db/schema.ts`).
2. **Partial Unique Index**: Enforced via PostgreSQL index:
   ```sql
   CREATE UNIQUE INDEX IF NOT EXISTS uq_active_doctor_slot
   ON appointments (doctor_id, slot_start)
   WHERE status = 'CONFIRMED';
   ```
3. **Migration Strategy**: Migrations are tracked as versioned `.sql` files generated by `drizzle-kit`, and can be auto-applied during bootstrap using the direct connection string (`DATABASE_URL_UNPOOLED`).

## Consequences

- **Positive**: Extremely fast startup times, zero binary dependencies, perfect Neon compatibility, and automatic TypeScript types for all 8 entities.
- **Negative**: Developers must maintain schema changes in `schema.ts` and run `drizzle-kit` for versioned migrations.
